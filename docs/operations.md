# Эксплуатация

## Обновление

Данные лежат в Docker volume `creds-data`, ключи в `.env`. Обновление кода их не трогает.

```bash
# 1. бэкап (см. раздел ниже)
# 2. новая версия кода
git pull                      # или конкретный релиз: git checkout <тег>
# 3. пересобрать и запустить
docker compose up -d --build
```

Если установка сделана из архива без git: скачайте архив новой версии, распакуйте в новую папку,
скопируйте в неё свой `.env` из старой (в нём ключи, без него данные не прочитать) и выполните там
`docker compose up -d --build`. Данные лежат в Docker volume и от смены папки не зависят, пока у проекта
то же имя папки (иначе Docker создаст новый, пустой volume). Перед этим сделайте бэкап.

Чего не делать:

- `docker compose down -v`. Ключ `-v` удаляет volume с базой.
- Менять или терять `ENCRYPTION_KEY`. Без него сохранённые пароли не расшифровать.
- Править в репозитории `docker-compose.yml`, если хотите свои настройки: они будут мешать `git pull`.
  Для своих настроек создайте рядом `docker-compose.override.yml`, Compose подхватит его сам.

После обновления загляните в админку и откройте страницу участника любого мероприятия кнопкой «Вид участника».

## Бэкап и восстановление

Бэкап базы:

```bash
docker compose exec web python -c "import sqlite3;s=sqlite3.connect('/app/data/creds.db');s.backup(sqlite3.connect('/app/data/backup.db'))"
docker compose cp web:/app/data/backup.db ./backup.db
```

Храните вместе с бэкапом отдельную копию `ENCRYPTION_KEY`, но не рядом с ним в одном месте:
у кого есть и то и другое, тот может прочитать пароли. Без ключа бэкап бесполезен.

Восстановление сводится к тому, чтобы положить файл бэкапа на место `creds.db` и запустить сервис с тем же
`ENCRYPTION_KEY`, которым он был сделан. Остатки журнала SQLite (`creds.db-wal`, `creds.db-shm`) рядом с
подменяемым файлом должны быть удалены. Эту процедуру вы выполняете сами, поэтому заранее отработайте её на тестовой
установке, а не в день мероприятия.

## Настройки

Хранятся в `.env`. Полный список с пояснениями есть в `.env.example`.

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `SECRET_KEY` | создаёт `setup.sh` | подпись cookie-сессий, не короче 32 символов |
| `ENCRYPTION_KEY` | создаёт `setup.sh` | ключ шифрования паролей рабочих мест |
| `MIN_PASSWORD_LEN` | 6 | минимальная длина пароля администратора |
| `PENDING_TTL_MIN` | 30 | через сколько минут протухает неактивированный код |
| `MAX_PENDING` | 1000 | потолок неактивированных кодов, старые вытесняются |
| `UI_TZ_OFFSET_HOURS` | 7 | часовой пояс для показа времени |
| `TRUST_PROXY`, `COOKIE_SECURE` | выкл | включить за reverse-proxy с HTTPS |
| `LISTEN_ADDR`, `HTTP_PORT` | `0.0.0.0`, `8765` | адрес и порт на хосте |

Ключи можно передать не только через `.env`, но и как Docker secret: для любой переменной поддерживается вариант
`ИМЯ_FILE` с путём к файлу.

За reverse-proxy с HTTPS задайте `TRUST_PROXY=1` и `COOKIE_SECURE=1` (подробности в разделе про развёртывание).
`LISTEN_ADDR` и `HTTP_PORT` читает `docker compose` из того же `.env`, приложение их не использует.

## Если что-то пошло не так

- **Красная плашка в админке «ENCRYPTION_KEY не подходит к данным» или ошибка «Данные нельзя расшифровать»
  у участника.** В `.env` стоит не тот ключ, которым записаны данные. Верните прежний ключ.
  Если прежний потерян, данные не восстановить: удалите их (`docker compose down -v`, это сотрёт базу)
  и введите заново.
- **Не заходит под админом.** Если вы ни разу не создавали админа, выполните `create-admin` (см. развёртывание).
- **`docker` не найден или нет доступа к сокету в WSL.** Включите интеграцию Docker Desktop с вашим дистрибутивом
  WSL и добавьте пользователя в группу `docker`: `sudo usermod -aG docker $USER`, затем перезапустите WSL.
- **Логи:** `docker compose logs -f web`.
